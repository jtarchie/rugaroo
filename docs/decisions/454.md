# Decision 454

**Rule:** A String ivar that its own class reads `length`/`size`/`[]` of gets a per-object cache field holding `rbStrLenA`'s length and ASCII bound for the String it currently holds (keyed by the String's data pointer and length, swapped atomically, Strings of 32 bytes or more only), so `@s.length` and `@s[i]` stop rescanning; a `String?` returned from a method stays a `*String`.

**Indexed String ivars** (#139; amends decision 399; 2026-11-13). *See also decisions 337, 396.*

Decision 399's loop hoist computes a loop-invariant String local's length and ASCII bound once, but spinel's bm_json_parse indexes the ivar `@input` from `peek`/`advance`, outside any loop the hoist sees: every call rescanned the input (`rbASCII`).

- **The cache.** `strCached`: a String ivar (not `String?`) of a struct class (not a value class, whose methods read a copy) that a method of that class, in program code, calls `length`, `size` or `[]` on gets a field `<field>C_ unsafe.Pointer`. `cachedIvarStrCall` turns `@s.length` into `rbStrCacheLenA(&self.sC_, @s)` and `@s[i]` / `@s[i, n]` into decision 399's `rbStrIdxA`/`rbStrSubA` with the cached bound.
- **Why it cannot go stale.** The entry is keyed by the String's data pointer and length; Go strings never change in place (decision 395's setbyte needs a String nothing else holds), so any write to the ivar (an attr writer, `instance_variable_set`, `dup`'s copy, Marshal) gives the read a different key and a rescan. No write site has to know about the cache.
- **Threads.** Readers of one object swap whole immutable entries with `atomic.LoadPointer`/`StorePointer`: no lock (memory: no global locks), no torn read, clean under `-race`. A plain `unsafe.Pointer` field, not `atomic.Pointer`, so a struct copy passes vet's copylocks.
- **Short Strings skip it:** under 32 bytes the scan costs less than the entry.
- **`String?` by value (#139's third cost) is not built.** Measured on hand-edited Go (bm_json_parse, instructions retired, min of 7): a static table of one-character Strings in place of `String#[]`'s `&v` made it worse, 658M → 746M (GOGC=off) and 702M → 808M (GC on), since Go already keeps that allocation cheap there; the full `rbOpt[String]` representation would also widen every `Array[String?]` slot from 8 to 24 bytes (decision 396 measured +3.9% for wider tuples) and undo decision 448's `*String` keys. Left as is.
- **Measured** (instructions retired, GOMAXPROCS=1, GOGC=off, paired against a8c3baf3, min of 5-7): bm_json_parse 657.9M → 405.8M (−38%, output == MRI); bm_template, bm_csv_process, bm_wordfreq, `benchmarks/` strings, json, kramdown, liquid, objects within ±0.15%.
- **Proof:** `testdata/test/string_test.rb` `StrIvarCacheTest` (ASCII and non-ASCII values, reassignment, a short String, `dup`, four threads reading one object, built with `-race`) against MRI.
