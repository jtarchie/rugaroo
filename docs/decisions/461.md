# Decision 461

**Rule:** Each StringIO holds a `sync.Mutex`, and every StringIO method with a Go body locks it for the whole call, so calls from several threads are atomic as MRI's GVL makes them.

**A lock per StringIO** (2026-11-13; the user's call). *See also decisions 88, 403, 460.* `Thread.new` is a goroutine (decision 88), and StringIO's methods read and move `buf` and `pos` with no synchronization: eight threads each writing one digit kept 6 or 7 bytes in about 5% of runs, and some runs panicked with `slice bounds out of range` (at 391dfa41 as at 2fc4538a). ruby/spec's `library/stringio` "handles concurrent writes correctly" passed or failed by luck. MRI's GVL makes each StringIO call atomic.

- **The rule.** `mu sync.Mutex` is the struct's first field; each `%x{}` body in prelude/stringio.rb except `new` starts with `self.mu.Lock(); defer self.mu.Unlock()`. Ruby-level methods (`print`, `puts`, `<<`) call `write` once per piece, so each piece is atomic and pieces from two threads can interleave; that matches MRI, which may switch threads between those calls too. No body calls another locked method, so the non-reentrant mutex cannot deadlock on itself; a program's `to_s` that writes to the same StringIO from inside `write`'s conversion would, which MRI also gets wrong (it recurses).
- **Not a global lock.** One mutex per object (the "no global locks" rule forbids a process-wide one), built from Go's sync package (the Go-primitives rule).
- **Cost:** `benchmarks/format.rb` (StringIO writes in its loop), instructions retired, GOGC=off GOMAXPROCS=1, minimum of 5 paired runs: 1.2658G → 1.2704G (+0.37%). An uncontended Lock/Unlock pair per call.
- **Proof:** `testdata/test/stdlib_test.rb` `StringIOTest#test_concurrent_writes` (8 threads × 50 writes, 20 times: fails before, passes after); `library/stringio`.
