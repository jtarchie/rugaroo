# Decision 429

**Rule:** Layered output packages (core prelude, library preludes, gems, user) are proposed for Go build-cache reuse only, staged behind measured gates, with single-file `gen > main.go` staying the default output.

**Status: proposed, not implemented.** Nothing below is binding until a stage gate passes and this file is amended. *See also decisions 49, 88, 206, 210, 212, 213, 235, 377.* Evidence: `docs/research/compile-time-2026-11.md` (branch `compile-time`; sections "Package split: the dependency graph says no" and "The cache argument for layered packages") and `docs/research/scc/main.go` (`CONTRACT=1 [CUT=rbDyn] [ORIGIN=1] scc main.go`).

## 1. Goal, and what it is not

Go caches a compile per package, keyed by its source bytes and its imports' export data. Today every program is one `package main` (`emitProgram`, `decls.go`), pruned per program (decision 49), so any edit to user code, and any difference between two programs, recompiles all of it: tokenize is 46.5k funcs / 23 MB, ~53 s for `main` alone (research doc).

Benefit sought, exactly:
- **Incremental rebuild:** a user edit rebuilds only the top package; an unchanged gem rebuilds nothing.
- **Cross-program reuse:** the core prelude (and each library prelude) is compiled once per compiler version and shared by every program on the machine (the build cache is shared across module dirs under `-trimpath`, decision 88).

Not sought, and measured not to be had: **cold-build time** (the core is compiled once; the sum is not smaller) and **parallelism** (research doc: 80-91% of lines sit in one strongly connected core; `-c=4` = `-c=8`, so backend concurrency is already exhausted). If a stage shows a cold or parallel win, report it, but do not gate on it.

## 2. Layering

Each package imports only the ones above it in this table:

| package | contents | cache key |
|---|---|---|
| `rt` (core prelude) | what `prelude.rb` `require_relative`s plus `prelude/go/*.go`: classes, modules, interfaces, `Kernel`/`Object` bodies, helpers | compiler version |
| `rt/<lib>` (library preludes) | one package per `libs.go` entry (`set`, `json`, `bigdecimal`, ...), importing `rt` and whatever MRI's own file loads | compiler version + lib name |
| `gem/<name>` | one package per vendored or `-I` gem, compiled as user code today (`vendoredLibs`, decision 328) | gem file hashes + compiler version + the types it sees (3a) |
| `main` (user) | user file, the closed-world dispatchers, forwarders and Dyn wrappers (3a), per-program tables (`rbUnbox`, class-ID arrays) | the program |

Prior art that bounds the design (decision 210, "Phase 5 measured, not done", 2026-10-11): an unpruned core as a cached `rt`, dot-imported by `main`, took `05_word_count`'s own package from 1,370 to 20,844 functions and `116_cuba_web`'s from 33,244 to 82,797 (1.35 to 3.1 GB). Causes named there: Go recompiles a generic instantiation in every package that reaches it, an instantiated type drags its whole method set, `super_Foo_` embedding promotes every parent method, and 402 Dyn wrappers/markers on prelude types exist only per program and cannot be declared from another package. Decision 213 later cut unpruned core 33,072 to 17,640 funcs and cuba's split package 36,370 to 25,986, so the premise is partly stale; it has not been re-run on the layered shape proposed here. Stage 0 re-measures it before anything else.

## 3. The three blockers (measured), and the mechanism for each

### 3a. 3,019 prelude declarations point up at gem/user types

Research doc, `ORIGIN=1 scc` on tokenize: 3,019 prelude declarations (9%) reference gem/user declarations (11,966 func edges, 21,248 type edges, 707 var edges; 7,655 distinct targets, led by `AST_NodeI`, `Prism_*`, `RuboCop_AST_*`). They are the closed-world pieces: `rbSend_<Owner>_<Name>` switches (`dispatch.go`, decisions 212/213: Kernel/Object arms name every program class), forwarders, `Dyn` wrappers and `rbDyn*` dispatchers (`dynamic*.go`), whole-program tables.

Mechanism: **hoist, don't call up.** A declaration whose body names a class outside its own layer is emitted into the top package; `rt` calls only its own layer directly, and higher layers through Go interfaces.
- Dispatchers (`rbSend_*`, `rbDyn*`, `DynName`): emitted in `main`. A call in a gem or `rt` body to a name overridden above its layer cannot be a direct switch; it takes the interface path (decision 212 already keeps the Go method when a name is reached through a Go method set). This **adds methods per class**, which 212/213 removed (forwarders 9,122 to 2,086). Expect part of that back, but only for names a lower layer actually calls on a higher layer's type, which is exactly the upward-edge set.
- Hook variables set in `init` are not proposed as the default: they sit next to the no-map-dispatch constraint and cannot inline (open question 2).
- Exports: cross-package access needs capitals, and an interface with an **unexported method can only be implemented inside its own package**. Every method in an `rt` interface must therefore be exported. `naming.go`'s operator table is injective against camel-cased names (decision 3); the export pass must be too (proposal: a reversible `Rb` prefix for `rb*` helpers, `_ClassID`-style markers become `X_ClassID`), built from the one declared-name set in `format.go` next to `addFrameLabels`. Dot-import keeps generated bodies unchanged.
- Generics across the boundary: decision 210 made `plainSelf` bodies non-generic because a generic "is recompiled by every package that instantiates it". 304 generic free funcs remain in cuba. `Self`-generic module funcs (decision 377, `specializeSelf`) instantiate in the calling package. Mechanism: instantiate in `main` and accept the duplicated compile, gated at stages 0-1. The risk is compile size, not speed (same GC shapes).
- Speed risk: `main` to `rt` calls are direct and inline across packages from export data under the same budget as now. The risk is interface calls where today there is a switch; gated by instructions retired (stage 1).

### 3b. 624 methods on prelude-origin types from reopened classes

A gem/user `class Integer; def foo` (and generated wrappers) puts a method on a type declared in `rt`; Go forbids that.

Mechanism: a reopened core class's added methods compile as **free funcs in the reopening layer** (`Integer_Foo(self *Integer)`, the shape decision 210 already uses), calls resolve statically (closed world: the receiver type is known at the call site), and a dynamic call goes through the top package's dispatcher (3a). An override of a core method that `rt` code itself calls (decision 206 adapters) is **pinned**: `rt` cannot see it, so it must go through an interface method on the core type or be rejected. Where the compiler cannot place a pinned reopening, the layered build fails with a message naming it; it never changes semantics, and the single-file default still compiles it. Speed: static calls match forwarders that inline; dispatcher switches are the existing 212 form.

### 3c. The prelude text differs per program (decisions 49, 377)

Pruning (`formatGo`, `prune.go`) and specialization (`specializeSelf`) make the prelude text a function of the program, so there is nothing stable to cache.

Mechanism: **layered `rt` is emitted unpruned and program-independent**: exported names, no per-program tables, no specialization copies (those live in `main`). Per-program pruning of `rt` moves to the linker (research doc: ~6.4k of 46.5k funcs are already absent from tokenize's linked binary). Pruning still runs on `main` and on a gem package's own text. Cache key for `rt`: compiler build ID plus sha256 of the embedded prelude; the text is deterministic, and its `//line`s are pinned to `:1` as in decision 88 (`stablePreludeLines`) so a line shift keys nothing, with the file name kept for backtraces.
- One-time cost is **unmeasured**: `RUGAROO_NO_PRUNE=1` hello world does not build (86,940 lines, 9,928 funcs, `undefined: BigDecimal` from library-gated types, research doc). Decision 213 reports unpruned core at 17,640 funcs, 656 MB and ~3.1 s of compile as of its measurement, taken before library gating. Library-gated types must move to `rt/<lib>` for the unpruned core to build at all.
- Alternative: prune `rt` to the union reached by a fixed profile (3-4 named tiers). Cheaper to compile, but the key becomes the profile and a program outside it falls back to single-file. Not first.
- Speed risk: none in generated code; cache and binary size grow (to be measured, not assumed).

## 4. Compiler pipeline changes

- `compiler.go` / `emitProgram` (`decls.go`): emit per layer. Every `Class` and method carries its defining file (`isPrelude()`, `gemFile`, the `//line` origin `scc` uses), so layer is a function of origin: one `layerOf(decl)`, and `emitClassType`, `emit_class.go`, `emit_classmeta.go`, `emit_consts.go`, `emit_adapters.go`, `emit_generics.go` and `dispatch.go` write to a per-layer buffer instead of `c.out`. Dispatchers, forwarders and Dyn wrappers always go to the top buffer.
- `format.go` `formatGo`: prune/sweep per package; std-import table per file; `specializeSelf` on `main` only; one export rewrite across all buffers.
- `reach.go`: reachability spans packages for `main` and gems (as now), not for `rt`.
- **Output.** Single file stays the default and the supported contract: `rugaroo gen > main.go` builds with `go.mod` alone. A layered output is a directory and cannot go to stdout: `rugaroo gen -out dir` (or `build -layered`) writes `dir/go.mod`, `dir/main.go`, `dir/rt/*.go`, `dir/gem/<name>/*.go`, no dependencies (stdlib-only). Without the flag nothing changes. `docs/cli.md` gets the row (`TestCLIDoc`), `docs/support.md` the tier (`TestSupportDoc`; experimental).
- Cross-program sharing needs one import path for `rt` across programs: a fixed module path with `-trimpath`, written once to `os.UserCacheDir()/rugaroo/rt-<key>/` and `replace`d into `dir/go.mod`.
- Lint/vet/gofmt: `.golangci.generated.yml` correlates `//nolint` by adjusted line (memory: generated-lint nolint coincidence), so per-package files change which lines match. The layered lane lints each package with the same rules (no loosening); `go vet ./...`; gofmt already runs in-process per file.
- Tests: a separate lane (`RUGAROO_LAYERED=1`, like `RUGAROO_CGO`/`RUGAROO_INT_OVERFLOW`) over the whole suite against MRI; it supplements, not replaces, the default lane.

## 5. Staged migration, gates, stop condition

Each stage ends with its measured numbers appended to this file. Thresholds are proposals (baselines to be taken at stage 0), not measurements.

- **Stage 0 (no compiler change).** On generated tokenize, `116_cuba_web` and `05_word_count` output, hand-split into `rt` / `main` by `ORIGIN` in a scratch module: hoist `rbSend_*`, `rbDyn*`, `Dyn*`, forwarders and tables into `main`, export by sed. Gates: (a) `docs/research/scc` (go/types) reports 0 errors and `ORIGIN=1` reports **0 prelude-to-upper edges**; (b) the split builds; (c) re-run decision 210's measurement on the post-213 core: `05_word_count`'s `main` package <= 2x today's compiled functions (2,065, `TestCompileCost`), where 210 saw 15x. If (c) fails and the causes (generic re-instantiation, method-set drag) have no 3a mechanism, stop.
- **Stage 1 (core `rt`; hello world, `05_word_count`, then cuba).** Implement `layerOf`, the export pass and `-out dir` for the core only; gems and libs stay in `main`. Gates, medians of 3 on this machine: (1) warm user-edit rebuild (change one literal, `rt` cached) <= 35% of today's warm whole-program build for `05_word_count`, <= 60% for cuba (its gems are still in `main`); (2) one-time `rt` cold build <= 3x today's cold hello world, and its key identical across two different programs; (3) runtime: instructions retired (GOMAXPROCS=1, decision 377's method) within +1% on every `benchmarks/` program, allocations not up; (4) minitest/run/examples equal to MRI in the layered lane; (5) default single-file output byte-identical to before.
- **Stage 2 (library preludes).** One package per `libs.go` entry. Gate: adding `require "json"` leaves the `rt` key unchanged and rebuilds nothing in `rt`; per-lib cache hits across programs; same speed and suite gates.
- **Stage 3 (gems).** `vendoredLibs` and `-I` gems as packages, plus 3b. Gate: examples 123 (kramdown) and 124 (liquid): a user edit leaves every gem package a cache hit, warm rebuild <= 25% of today's; the 624 reopened methods on tokenize resolve to free funcs plus dispatcher arms, any pinned ones listed with the fallback.
- **Stop condition.** Amend this decision to "rejected, with these measurements" if: stage 0(c) fails with no mechanism; stage 1 misses gate (1) (the incremental win does not pay for the export rewrite and the second lane); any benchmark regresses >1% in instructions retired that a hoisting choice cannot recover; or the lane needs map-based dispatch or loosened Go typing to typecheck. Stages 0-1 ship only behind the opt-in directory output, so stopping costs the flag and the lane.

## 6. Alternatives considered

- **Do nothing; rely on inference-round work.** Levers 1-3 in the research doc cut `gen` time (rounds are 60% of gen). They give no incremental `go build`: a user edit still recompiles 23 MB. Complementary and cheaper; do them regardless.
- **Function-level incremental via gcflags.** Go has no function-granular compile cache. `-c` is concurrency inside one package and is saturated (`-c=4` = `-c=8`); several files of one package change nothing for the compiler.
- **Share Dyn-wrapper bodies (research lever 5b).** 3,549 distinct of 10,743 Dyn wrappers on tokenize, ~15% fewer funcs (build time scales with funcs, decision 235). Orthogonal, one package, but one extra call per dynamic dispatch unless inlined; needs its own A/B.
- **Package split for parallelism.** Rejected by the research doc (80-91% of lines in one SCC, <= ~20% movable).
- **Cached `rt` with hook variables for whole-program tables** (the 2026-10-11 prototype). Measured worse (decision 210). This proposal hoists dispatchers instead of hooking; stage 0 re-measures it.

## 7. Open questions (user only)

1. **Is an opt-in directory output acceptable, with the single file as default?** Recommend yes: a stable `rt` import path across programs is the only way to share the cache, and single-file stays the `> main.go` contract (and the wasm playground path, which has no user cache dir). Stage 1's stop condition bounds the cost.
2. **May a lower layer reach a higher one through a function-typed variable wrapping a compiled type switch, set in `init`, where an interface method is impossible?** Recommend no initially: interface methods and top-package hoisting only; revisit if stage 0 leaves a residue of edges. It sits beside the no-map-dispatch rule and cannot inline.
3. **Is a slower cold hello world acceptable (unpruned `rt` compiled once, size unmeasured) for fast incremental builds?** Recommend yes if stage 1 shows <= 3x cold and a cache hit thereafter (gate 2): the daily loop is edit-rebuild, and `rt` builds once per compiler version.
4. **Do library-gated types move to `rt/<lib>` packages, or does the core stay pruned to fixed tiers?** Recommend `rt/<lib>`: a lib has an obvious key, a tier makes the key a profile choice.
5. **Does the layered lane lint each package with `.golangci.generated.yml` unchanged?** Recommend yes, no new `//nolint` budget ("fix codegen instead of loosening it").
