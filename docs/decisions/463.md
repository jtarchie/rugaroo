# Decision 463

**Rule:** A compiled program, from its first package initializer on, puts its first collection off to about 32 MiB (GOGC 800 until it runs), then holds a 16 MiB heap ballast that is never written with GOGC back at 100, so later collections also wait for 32 MiB; `GOGC` or `GOMEMLIMIT` in the environment turns it off.

**GC ballast** (2026-11-15). *See also decisions 151, 240.*

Go starts collecting at a 4 MB heap and again at every doubling of the live heap. A Ruby program with a few MB of live data and a high allocation rate (every `map`, every String) therefore collects dozens of times in a run that lasts a fraction of a second: `benchmarks/liquid.rb` ran 39 collections, kramdown 50, compiled rubocop on 20 files 64. MRI's own heap starts far above 4 MB (its RSS on `benchmarks/collections.rb` is 54 MB).

- **The mechanism.** A package variable initializer in `prelude/go/compiler_gc.go` (amended 2026-11-16, below; it was `rbGCStart`, the first call of the generated `main`) sets GOGC to 800 (Go's 4 MB minimum heap times 8) and leaves an unreachable object whose finalizer, run after the first collection, allocates `rbGCBallast = make([]byte, 16<<20)` into a global and sets GOGC back to 100. The collector counts the ballast as live, so every later heap goal is at least twice its size; it holds no pointers, so it is never scanned, and it is never written, so the operating system never backs it with memory.
- **Why not the ballast from the start.** Allocating 16 MiB at start-up passes Go's 4 MB trigger and starts a collection of its own: 2M instructions on a program that runs 20M (spinel's micro-benchmarks: +8%). A program that never allocates 32 MiB now never collects and pays nothing (`bm_nbody` 20.2M before and after).
- **Why not `GOGC`.** Decision 151 rejected a higher default `GOGC` because it doubles a large heap's peak. A first version of this decision raised `GOGC` only while the live heap was small and retuned from a finalizer after each collection: it measured `benchmarks/bignum.rb` at 214 MB RSS against 12 MB, since Go scales the globals and stacks into the goal by the same percent and the retune comes one cycle late. GOGC 800 is in force only until the first collection, whose goal Go recomputes when the finalizer sets 100. The ballast adds a constant: a heap goal of `2 x (live + 16 MiB)`, so at most 32 MiB of headroom whatever the live heap is.
- **TinyGo** has no `GOGC` to tune: its side of `prelude/go` has no such initializer (decision 443).
- **Measured** (instructions retired, macOS arm64, `GOMAXPROCS=1`, against main be30d759; RSS before → after): strings 287M → 183M (−36%, 15 → 22 MB), objects 378M → 295M (−22%, 19 → 27 MB), collections 1,424M → 1,140M (−20%, 44 → 51 MB), json 1,990M → 1,604M (−19%, 32 → 49 MB), liquid 2,186M → 1,818M (−17%, 19 → 39 MB), kramdown 4,659M → 4,076M (−13%, 30 → 47 MB), regexp 3,027M → 2,708M (−11%, 21 → 38 MB), bignum 516M → 462M (−10%, 11 → 34 MB), binary_trees 66M → 62M, mutex 536M → 533M, thread_churn 385M → 396M (+3%, noise of its scheduling). Rows whose heap never reached 4 MB (fib, hash, math, splay) are unchanged.
- **What it costs:** up to about 20 MB more resident memory on a program that allocates past 4 MB, none on one that does not.
- **Before package initialization** (amended 2026-11-16; `docs/research/startup-2026-11.md`). Go runs a program's package variable initializers before `main`, so anything they allocate was collected at Go's 4 MB goal before `rbGCStart` had run: compiled rubocop, whose 463 Regexp literals compiled there, ran six collections before its first line (its load: 1,166M instructions, 1,064M with `GOGC=800` in the environment). The set-up is now itself a package variable initializer, declared in `prelude/go` and so ahead of the program's own variables, which go out last. `--regexp-compile=lazy` (decision S1) removes most of what those initializers allocated; this covers `eager` and any program whose constants are large. hello-world is unchanged (18.0M instructions, 4.1 MB, no collection), as are `benchmarks/` strings, objects, regexp, collections, json and bignum within their run-to-run spread.
- **Tried and not kept: the collection right after the ballast.** The finalizer allocates 16 MiB and sets GOGC 100 while the collector's goal is still twice the live heap it last marked, so a second collection starts at once (rubocop: `64->65->13 MB`, then 3 ms later `30->31->30 MB`). Two ways to avoid it were measured. (1) Keep a computed GOGC for one cycle, so that the goal is twice (live + 16 MiB), and set 100 from a second finalizer: the second finalizer runs late on a busy program, the computed percent (3,300 when 1 MB is live) then scales the next goals, and `benchmarks/bignum.rb` went from 40-55 MB to 120-200 MB resident and 460M to 490-535M instructions; the retune this decision first rejected, again. (2) Allocate the ballast up front under GOGC 1200: collections −11% and json −6%, but bignum +3% and 68-88 MB resident, regexp +2%, and every program pays the allocation. The extra collection stays.
