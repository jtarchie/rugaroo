# Decision 470

**Rule:** A gem method with no signature of its own takes the one a sig file declares for its name on a superclass that does not define the method; a tuple held in a union is called and looped over as the Array it is.

**Signatures a superclass only declares** (amends decisions 160, 241, 306; 2026-11-16). *See also decisions 331, 444, 457.*

A cop's `on_send(node)` is called from one place, the Commissioner's `cop.public_send(callback, node)`, with the callback's name in a variable: a dynamic use, which widens a parameter but never types it (decision 331). So `node` was untyped in every callback of every cop, and with it each `node.children`, `node.type`, `node.loc` and everything computed from them: of rubocop's gem parameters, inference typed about 1,750 in all (`docs/research/runtime-speed-2026-11.md`). `Cop::Base` defines none of the callbacks, so an RBS line for it reached no method: a sig-file entry was applied only to a def of that class (decision 160) or, through it, to an override (`inheritSignature`).

- **`ancestorSig`** (`signatures.go`, from `resolveMethod`): a gem method with no `#:` and no sig-file entry of its own walks its superclasses; the first that has a sig-file declaration of the name and no def of it gives the method that signature, when it is a single overload fitting the def's parameters (decision 427's test). A superclass that defines the method ends the walk: that is `inheritSignature`'s case. The method is `declared` (decision 241): its parameter is the author's type, checked where an untyped value is passed.
- **Not used for rubocop.** `sig/gems/rubocop/rubocop.rbs` was generated from `Parser::Meta::NODE_TYPES` and rubocop-ast's `NODE_MAP` (`def on_<type>: (RuboCop::AST::Node node) -> untyped` and `after_<type>`, 280 lines) and measured: the binary printed what MRI prints on 280 files, but cops raised on stderr (`Lint/DuplicateElsifCondition` on every file: `node = node.else_branch; break unless node&.if_type?` reassigns the parameter to nil, and a parameter declared `Node` is not nil, so `&.` is a plain call), and instructions went up, not down: `dir20` 13,950M → 14,330M, 80 layout cops 42,400M → 42,705M. A typed `node` alone buys nothing there: what a cop calls on it is mostly a method of a node subclass or a generated node-pattern matcher, both dynamic either way, and the callback's entry gains an assertion. The file was removed; the rule stays for gems whose base class documents callbacks it does not define.
- **Does not cover** a callback defined in a module a cop includes (`CheckAssignment#on_lvasgn`): a module has no superclass to ask.
- **A tuple in a union is an Array** (decision 444's list): a gem's mixed literal (`Node.new(:send, [left, right, :name])`) is a Go tuple, which a union keeps as it is (decision 150); `children.each { }` on that member raised NoMethodError. `genUnionIterCall` loops over its `_ToAny()`, `unionCall` calls on it, and a dispatcher that meets a bare tuple re-dispatches on the Array (`rbTupleArray`).
- **Measured.** A 60-line gem of this shape (`testdata/run/gem_callbacks`): 10 → 3 dynamic calls, 3,130M → 2,567M instructions (MRI 6,638M).
- **Proof:** `TestRun/gem_callbacks` against MRI.
