# Decision 469

**Rule:** `a[i] op= v` on an `Array[Integer]` or `Array[Float]` with an Integer (or Integer?) index inside the Array reads and writes the element in place behind one bounds test; any other index takes the read-then-write path.

**Element op-assign in place** (amends decisions 342, 350; 2026-11-16). *See also decisions 396, 402, 489 (a nilable element operand fuses too).*

`counts[b] += 1` compiled as `a[i] = a[i] + v`: the read tested the index for a negative value and for the bound, the write tested the bound again, and under `--nil-check=runtime` (or in gem code) an `Integer?` index was unwrapped three times. Decision 350 already fuses the same statement on a Hash (`rbHashSlot`).

- **`genFusedElem`** (`expr_hashfuse.go`), from `genIndexOpWrite` when the receiver is an Array of Integers or Floats, the index an Integer or Integer?, and the operation keeps the element's type (`fuseResult`, as for a Hash): `if i := idx; uint64(i) < uint64(len(a.s)) { v := a.s[i] op value; a.rbCheckFrozen(); a.s[i] = v } else { the read-then-write }`. The frozen check follows the new value, as `[]=` runs after it in Ruby. A negative index, one past the end (nil has no `+`: NoMethodError) and a nil index all take the old path, which answers as before.
- **Measured** (spinel's `bm_histogram`, 200M element updates, `--nil-check=runtime`): 0.87 s → 0.77 s, 11,439M → 11,036M instructions; spinel 0.39 s. What is left per update is the two element loads' bounds tests, the frozen flag read twice and the overflow test; hoisting the flag and the bounds out of a counted loop is the next step, not taken here.
- **Proof:** `testdata/test/array_test.rb` `ArrayElemOpAssignTest` (in range, negative index, past the end, frozen, the statement's value) against MRI.
